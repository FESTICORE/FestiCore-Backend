# API 명세 v0.1 구현 대조

## 2026-10-22 구현·검증 상태

현재 소스에는 공개 축제·팩/상세/라이브, 인증·내 정보, 깃발·기수, 크루, 일정, 기기·알림, 메트릭, 관리자 축제·크롤링·계정·감사 API 컨트롤러가 있다. 이는 **경로 구현 확인**이며 개발·운영 배포에서 모든 요청이 정상 동작한다는 증거는 아니다. 현재 컨트롤러의 HTTP 메서드 선언은 97개다.

- 공개 팩 갱신 WebSocket은 [PR #49](https://github.com/FESTICORE/FestiCore-Backend/pull/49)로 `develop`에 병합했다. Origin·연결 상한·읽기 전용·ping/pong·버전 중복 제거 및 실제 업그레이드 테스트를 추가했다. 앱의 재연결/오프라인 저장과 Railway WSS 프록시 동작은 아직 검증하지 않았다.
- 관리자 발행의 초안 버전 조건부 갱신은 [PR #48](https://github.com/FESTICORE/FestiCore-Backend/pull/48)로 병합했다. Next.js AdminWeb은 별도 저장소 [PR #1](https://github.com/FESTICORE/AdminWeb/pull/1)로 `develop`에 병합했다. 운영 Google OAuth 설정 및 실제 로그인은 별도 확인이 필요하다.
- 공개 축제 목록의 실제 데이터량, 원더리벳·YES24·멜론·NOL 등 각 원본의 최신 파싱 결과와 매일 00:00 KST 작업 실행은 개발·운영 DB와 스케줄 로그로 확인해야 한다. 코드 존재만으로 데이터 수집 완료를 선언하지 않는다.
- 제공된 Notion 페이지 `400c7b04-af13-80e5-b058-d369c47c0b6c`는 현재 연결 계정에서 `object_not_found`(404)로 조회돼 원문 대조를 완료하지 못했다. 아래 로컬 PDF 대조 결과의 범위와 구분한다.
- Railway 개발·운영 배포, 실기기 APNs, 이미지 버킷 쓰기/읽기, 모바일 재연결 및 실제 PostgreSQL 동작은 각각 별도 실환경 검증이 남았다.

## 2026-10-21 재점검

로컬 PRD v16.1·API v0.1 PDF와 코드를 대조했다. Notion 기능 명세서는 연결 검색에서 원본을 찾지 못해 대조 범위에 포함되지 않았다. 다음 항목은 완료로 표시할 수 없다.

| 우선순위 | 남은 계약 차이                                                                                                                                                              |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1       | 팩 발행·롤백의 `pack.updated` 푸시 대기열은 구현. 기존 CDN 캐시 객체의 즉시 무효화는 미구현이며 CDN 제공자·퍼지 설정을 확인해 연결할 것. 실제 APNs 전송도 배포 후 검증할 것 |
| P1       | `POST /crews/:id/status`의 `Idempotency-Key` 재전송·충돌 처리는 구현. PostgreSQL 실동작과 배포 경로를 검증할 것                                                             |
| P2       | 발견 축제의 `discovered`·`packVersion: 0`을 앱 계약에 반영할 것                                                                                                             |
| P2       | Railway CDN이 요청의 `no-cache`를 무시한 실측에 따라 목록 응답을 `public, no-cache, must-revalidate`로 변경. 앱은 `If-None-Match`로 변경 없는 목록에 304를 받음 |

추가 사용자 요구: 원더리벳 등 티켓 소스 파싱과 실제 데이터 저장, WebSocket, Redis 캐시, 아티스트 이미지, 불안정한 네트워크용 오프라인 갱신, 개발·운영 배포 및 보안 검증. 이는 위의 API 라우트 존재와 별도로 완료 여부를 확인한다.

사용자가 이후 변경한 계약은 원본 PDF보다 우선한다. Google·Apple 로그인 통합, 기기 헤더 식별, 관리자 인증 API 불필요 지시를 원본 PDF의 경로 누락으로 계산하지 않는다. 기존 관리자 보호 장치를 제거할 때에는 외부 공개 경로의 접근 제어를 함께 검증한다.

로컬 API·기능 PDF의 경로 차이도 확인했다. API PDF p25의 직접 `PUT /admin/festivals/{id}/pack`은 같은 문서 p30–31의 초안 수정→발행 계약으로 구현되어 있으며 직접 팩 쓰기 경로는 제공하지 않는다. API PDF p22의 `DELETE /auth/session`은 `POST /auth/logout`으로 대체했다. 기능 PDF p9의 `POST /crews/{id}/join`과 API PDF p19의 `POST /crews/join`은 원본끼리 다르며 구현은 API PDF 경로를 따른다. 이 차이를 별도 누락 기능으로 계산하지 않되 클라이언트 계약에는 현재 경로를 사용한다.

## 이번 API 완성 작업의 순서

1. 테스트 푸시와 관리자 계정 관리 API의 요청·응답·권한을 구현하고 Swagger·E2E를 대조한다.
2. 관리자 전용 로그인 경로와 세션 쿠키를 제거하고 일반 로그인 Bearer JWT에 연결된 `owner` 권한으로 관리자 계정 관리 API를 보호한다. 외부 공개 관리자 쓰기 API의 역할·Origin 검사는 유지한다.
3. 모든 명세 경로를 현재 라우트와 다시 대조하고, CI를 통과한 기능 PR부터 차례로 스쿼시 머지한다.
4. Railway 장애가 해제되면 개발 서버에서 마이그레이션·Swagger·API 응답을 검증한다.

이미지 입력 미리보기는 Docker 런타임의 Tesseract 한국어·영어 OCR을 사용한다. 추출 결과가 불명확하면 초안을 만들지 않고 원문을 `unparsed`에 보존한다.
